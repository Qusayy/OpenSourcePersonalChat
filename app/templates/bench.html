Why it is this fast

Generating a token means reading every weight in the model once. At Q4_K_M that is about a gigabyte per token, so throughput tracks memory bandwidth far more closely than clock speed: tokens per second ≈ effective bandwidth ÷ model size. Two shared vCPUs reach single-digit gigabytes per second, which lands this model in the region the charts above show.

That formula is also the whole argument for 4-bit. Dropping from 16-bit to 4-bit weights cuts the bytes moved per token by roughly four, and the speed rises by roughly the same factor — which is what makes a 1.5B model usable here and a 7B model hopeless.

Prefill behaves differently. Reading the prompt is a batched matrix multiply, so it is compute-bound and processes many tokens per pass. That is why a long prompt costs seconds rather than minutes, and why follow-up turns are quicker still: llama.cpp keeps the KV cache from the previous turn and only prefills what is new.

The last piece is the queue. With two cores, two generations running together finish later than the same two run back to back, so this server serialises them and tells you your position instead of pretending to be parallel.
