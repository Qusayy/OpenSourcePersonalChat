Why it is this fast

Generating a token means reading every weight in the model once. At Q4_K_M that is about a gigabyte per token, so throughput tracks memory bandwidth far more closely than clock speed: tokens per second ≈ effective bandwidth ÷ model size. A pair of shared cloud vCPUs reaches single-digit gigabytes per second, which puts this model at around ten tokens per second there; a desktop's faster memory is why its row above sits so much higher.

That formula is also the whole argument for 4-bit. Dropping from 16-bit to 4-bit weights cuts the bytes moved per token by roughly four, and the speed rises by roughly the same factor — which is what makes a 1.5B model usable on a couple of shared cores, where a 7B model would manage a token or two a second.

Prefill behaves differently. Reading the prompt is a batched matrix multiply, so it is compute-bound and processes many tokens per pass. That is why a long prompt costs seconds rather than minutes, and why follow-up turns are quicker still: llama.cpp keeps the KV cache from the previous turn and only prefills what is new.

The last piece is the queue. Two generations running together fight over the same memory bandwidth and the same {{ info.n_threads }} model threads, and finish later than the same two run back to back, so this server serialises them and tells you your position instead of pretending to be parallel.
